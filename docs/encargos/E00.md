## 0. Contexto

AAL (Análisis de Apoyo Logístico) es una app web para el cliente em&e que soporta el AAL de un material del Ejército y genera los entregables del PALI desde una única base de datos. La norma que manda es la **NT 10/17** del Ejército de Tierra (configuración funcional física, codificación de tareas, ficheros SIGLE), con la S3000L aplicada parcialmente. La primera entrega al cliente cubre **RF-01 a RF-05** (configuración funcional normalizada, CONFUNFIS física, validación NT, artículos y selección de candidatos AAL con requisitos de tarea).

Este encargo **solo monta los cimientos**: no hay lógica de dominio, ni usuarios, ni pantallas de negocio.

**Antes de escribir código, lee:**

Como mínimo `AGENTS.md`, `rules/atexis-hard-rules.md`, `rules/python.mdc`, `rules/javascript.mdc`, `rules/security.mdc`, `styles/design-system.md` y `governance/guardrails.md`. 3. **La referencia de implementación es `Juanma-GA/brdp-manager`, rama `v2-multiproyecto`** (solo lectura). Es un proyecto del mismo autor, hecho con el mismo flujo y que ya cumple AACF. Reutiliza sus patrones adaptándolos, no los reinventes:

### 1.2 Backend mínimo
- FastAPI con `app/main.py` que solo ensambla. Sin `from __future__ import annotations` en ficheros de rutas.
- `core/config.py` con pydantic-settings (`DATABASE_URL`, `TEST_DATABASE_URL`, `CORS_ORIGINS` sin `*`, entorno).
- `core/errors.py`: errores saneados al cliente y detalle completo en el log.
- Logging estructurado JSON.
- SQLAlchemy 2 async + asyncpg; Alembic con la primera migración, que crea:
  - `app_parameter` (clave, valor JSON, descripción, actualizado por / en). Base de HR0: las lecturas pasan por un servicio que hace **deep-merge** (HR10) entre los valores por defecto y la BD; incluye una función `deep_merge` con tests.
  - `audit_log` (id, momento, usuario nullable por ahora, acción, entidad, id de entidad, material nullable, antes y después en JSON, IP). Un servicio `audit.record(...)` lo escribe; todavía no hay ninguna mutación que lo llame, pero queda probado con un test.
- Rutas: `GET /api/health` (estado de la app y de la BD, versión de migración) y `GET /api/version` (versión de la app y del AACF).
- `pyproject.toml` y lockfiles `requirements.lock.txt` / `requirements-dev.lock.txt` con uv y hashes, como en brdp-manager. Python 3.11+ (el mismo objetivo que brdp-manager).
- BD de tests propia (`aal_test`) con las mismas salvaguardas que brdp-manager (`_testdb.py`: nombre acabado en `_test`, distinta de `DATABASE_URL`) y los scripts `create_test_db.py` / `check_test_db.py`.
- Tests: unitarios de `deep_merge` y de `audit.record`, e integración de `/api/health` y `/api/version`.

### 1.3 Frontend mínimo
- **React 18** + **TypeScript strict** + Vite + react-router + @tanstack/react-query + **Zustand** + react-i18next + Tailwind.
- **shadcn/ui** inicializado (`components.json`, alias `@/`), con los componentes que use esta página (por ejemplo `card`, `badge`, `skeleton`). A partir de aquí, toda primitiva sale de shadcn/ui y nunca se hace a mano (AACF `styles/ui-kit.md`).
- **Tokens:** variables CSS de shadcn/ui (`--background`, `--foreground`, `--primary`, `--muted`, `--border`, `--radius`…) definidas en `src/styles/globals.css` con un tema **em&e**: neutros grafito tomados del logo y un acento accesible (WCAG AA), en claro y oscuro. Nada de hex en componentes. Tipografía Inter / JetBrains Mono vía `@fontsource`, como en brdp-manager.
- Un store Zustand mínimo (`src/stores/uiStore.ts`, por ejemplo con el estado del menú lateral) para dejar fijado el patrón: **sin middleware `persist`** (HR1).
- Logo en `public/brand/eme-group-logo.png`, en una cabecera mínima con el nombre "AAL — Análisis de Apoyo Logístico".
- i18n con `es` como único idioma poblado. Ningún texto visible fuera de los ficheros de traducción (HR15), y una utilidad `humanize` con test (HR21).
- Página única `/` que muestra el **estado real** de la API (`/api/health` y `/api/version`), con React Query y con estados de carga y error. No hay datos simulados.
- `src/services/apiClient.ts` centralizado (base `/api`; proxy de Vite al 8000 en desarrollo).
- **Nada de `localStorage` ni `sessionStorage`** (HR1). Añade un test que lo vigile en `src/` (también que no se use el middleware `persist` de Zustand), como hace brdp-manager.

### 1.4 Verificación y CI
- `npm run check` (lint + typecheck + build + `test:js`) y `npm run check:all` (+ `test:backend`), con `scripts/run-checks.mjs` adaptado de brdp-manager. Mismos códigos de salida: 0 = todo bien, 1 = algo falla, 2 = falta algo del entorno.
- Compatibilidad con Windows: tests equivalentes a los de brdp-manager (sin `/tmp`, `.venv/bin`, `ps` ni shell en los scripts de Node; `encoding=` en todo `open()` de Python; `.gitattributes` con LF).
- `scripts/verify-health.mjs` (playwright-core, Chromium real) que abre la app, comprueba que se ve "API conectada" con la versión, y hace una captura.
- GitHub Actions `.github/workflows/check.yml`: Postgres 16 como servicio y `npm ci` + `check:all`; más un paso de escaneo de secretos (gitleaks).
- `docker-compose.yml` **solo con Postgres 16** para desarrollo (opcional; el `CLAUDE.md` explica también cómo usar un Postgres local de servicio, como en brdp-manager).

## 3. Criterios de aceptación
1. `npm ci && npm run check:all` termina con código 0 en Linux, y los tests de compatibilidad con Windows pasan.
2. `alembic upgrade head` sobre una BD vacía crea `app_parameter` y `audit_log`; `alembic downgrade base` las elimina sin error.
3. `/api/health` devuelve 200 con estado de la BD y versión de migración; con la BD parada devuelve un error saneado, sin traza al cliente.
4. `verify-health.mjs` pasa y deja una captura de la página con logo y estado.
5. Ningún string visible hardcodeado; no aparece `localStorage` ni `sessionStorage` en `src/`; ningún hex en componentes.
6. CI en verde en el PR.
7. `git ls-files private/` solo devuelve `private/README.md`.
